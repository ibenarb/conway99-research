# Guard robustness repair 1.0.1 — 2026-09-16

## Observed incident

User-supplied reports identify run `matching_20260915_172002_018090`. It terminated after 7,843 seconds with `FileNotFoundError(2, 'No such file or directory')`, no collected results and eleven interrupted jobs. The last periodic status at 2026-09-15T19:30:24Z showed Windows free space 210.69 GiB, available Linux RAM 39.86 GiB, and about 1.2 MB campaign output. The observer's retained state at 19:30:45.2716683Z reported 226230288384 free bytes and `stop_reason: null`. The stop marker and heartbeat also had that time. No resource-limit stop is evidenced.

The old controller recorded only repr(exception), losing the FileNotFoundError filename and stack trace. Exact attribution is therefore impossible from the supplied reports. A transient telemetry-publication gap is a plausible cause, not a confirmed root cause. No new filesystem corruption has been established by these reports.

## Concrete weaknesses repaired

1. Windows telemetry previously used PowerShell Move-Item -Force to replace an existing file. The writer now uses the dedicated .NET File.Replace operation for an existing destination and File.Move only for first publication. Writer-side IOException retries are bounded to roughly two seconds. Microsoft API reference: https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace . We do not claim an absolute atomicity guarantee across WSL/DrvFs.
2. The Linux reader now retries missing, temporarily inaccessible, or incomplete JSON telemetry for at most two seconds. Every accepted state must still be fresh and above the disk floor, and explicit stop reasons still fail immediately. It never silently substitutes cached data. Persistent failures include the path and exception chain.
3. Observer data is placed under Windows LOCALAPPDATA/Conway99/guards rather than TEMP. This avoids reliance on generic temporary-file retention; deletion was not established as the original cause.
4. Windows heartbeat reads tolerate short IOException failures with the same bounded window. The 90-second missing-heartbeat policy is unchanged.
5. The Linux output-size scan tolerates disappearance of atomic-write `.tmp` files only; other observed stat failures propagate.
6. Full exception text, type, filenames and traceback are retained in summary.json and printed to driver.log. Controller and guard hashes are recorded in the new run configuration. Telemetry-read retry counts are visible in status and summary.

Windows reserve 50 GiB, Linux reserve 25 GiB, RAM reserve 4 GiB, solver memory/log/time limits and no-proof mode remain unchanged. The reference encoder, worker and matching mathematics are byte-identical to release 1.0.0. CNFs and the installed solver are reused after hashing. No current/old run directory is overwritten and no proof data is removed.

## Validation and limitations

Local regression controls passed for actual missing-then-created telemetry, injected missing/access/JSON failures, persistent missing telemetry, stale timestamps, low space and explicit stop reasons. A controller fault injection confirmed full path and traceback recording. The controller also completed eleven dummy test processes with UNSAT-style exit/status output; these were not SAT solver runs and establish only orchestration behavior.

Two initial attempts to repeat the old local real-CaDiCaL controller controls failed because the temporary build `/tmp/c2-cadical-build/build/cadical` no longer existed in this session. They did not run any research job. Rebuilding that unchanged solver was unnecessary for this guard fix; the replacement controller control uses an explicitly simulated solver. The existing Ryzen binary is separately hash-checked during activation.

The Windows File.Replace writer cannot be executed in this Linux build environment. `activate.py` therefore requires a 15-second real Windows/WSL observer exercise with at least three distinct fresh publications before activating the version. It does not run production solvers during that test. This short exercise is not proof against every overnight OS failure and does not test emergency process-group termination.

## Restart semantics

A new eight-hour run starts from the original inputs and seed zero. The interrupted search has no checkpoint, so its first roughly two hours are repeated rather than resumed. The mathematical eight-hour experiment was not completed; its failure should not be counted as an eight-hour timeout for any case. All eleven cases remain open based on the available records.
